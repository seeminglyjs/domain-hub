# 시맨틱 레이어(Semantic Layer) — 지표 정의를 한 곳에 두기

> 분류: 도메인 › 시맨틱 레이어 · 작성: 2026-11-10 · 실린 주간 노트: [2026-11-10](../../../weekly/2026-11-10.md) · [전체 색인](../../../README.md)

**한 줄 정의**: 매출 같은 업무 지표를 어떤 테이블에서 어떻게 조인 · 집계하는지 한 곳에 정의하고, 화면 · 보고서 · AI 에이전트가 모두 그 정의를 불러 쓰게 하는 계층입니다.

**그 주 소식과 연결**: 이번 주 Snowflake 가 발표한 Business Ontology 는 지표의 의미와 계산을 나눠 맡기는 구조여서, 시맨틱 레이어가 어디까지 맡는지 보여 주는 사례입니다.

## 1. 왜 필요한가

매출 같은 지표의 계산 규칙이 BI 도구(Business Intelligence, 대시보드와 보고서를 만드는 도구, 예: Tableau · Looker)마다 따로 있으면, 사업부마다 같은 매출(revenue)을 다르게 계산하게 됩니다. dbt(SQL 로 데이터 웨어하우스 안의 데이터를 가공 · 관리하는 오픈소스 도구) 문서도 이 문제를 시맨틱 레이어가 필요한 이유로 듭니다. 같은 이름의 숫자가 화면마다 다르면 보는 사람은 어느 숫자도 믿지 않게 됩니다.

예를 들어 매출 대시보드는 환불을 뺀 금액을 쓰고 월간 보고서는 환불을 넣은 금액을 쓰면, 보는 사람은 두 숫자가 왜 다른지 묻게 됩니다. 시맨틱 레이어는 이런 정의를 한 곳으로 모아, 어느 도구를 쓰든 같은 정의를 쓰게 합니다.

## 2. 동작 원리

dbt Semantic Layer 는 지표를 BI 도구가 아니라 모델링 계층(원천 데이터를 분석용 테이블로 가공하는 단계)에서 한 번 정의합니다. 사용자가 지표를 요청하면 MetricFlow 라는 엔진이 정의에 맞춰 필요한 조인을 처리합니다. 정의를 바꾸면 그 지표를 부르는 모든 곳에 반영됩니다.

Snowflake(클라우드 데이터 웨어하우스 회사)는 이번 발표에서 맥락을 세 층으로 나눴습니다. Business Ontology 는 승인된 의미를 저장하고, Semantic View 는 조인 · 필터 · 집계 같은 계산을 맡고, Cortex Sense 는 정의되지 않은 맥락을 추론합니다.

Snowflake 엔지니어링 블로그는 온톨로지가 수식을 저장만 하고 실행하지 않는다고 밝힙니다. 사람이 승인한 정의가 추론보다 우선한다는 점도 함께 적습니다.

## 3. 예시 장면

Snowflake 엔지니어링 블로그의 예시를 줄여 옮깁니다. 같은 '순매출(Net Revenue)' 이라도 재무 도메인은 환불과 할인을 뺀 인식 매출로, 영업 도메인은 계약 시점에 할인을 뺀 수주 금액으로 정의합니다.

사용자가 에이전트에게 지난 분기 순매출을 물으면, 에이전트는 두 정의를 보여 주고 어느 쪽인지 묻습니다. 사용자가 재무를 고르면 에이전트는 재무 도메인의 Semantic View 지표를 써서 답하고, 그 수치를 승인된(governed) 수치로 표시합니다.

답에는 내부 거래 송장과 테스트 계정이 빠진다는 안내도 붙습니다. 같은 이름의 지표가 둘 있어도, 어느 정의를 썼는지가 답과 함께 드러나는 장면입니다.

## 4. 실무에서 확인할 점

첫째, 매출 같은 지표를 계산하는 SQL 이 여러 서비스나 API 에 따로 적혀 있는지 확인합니다.

둘째, 같은 이름의 지표가 화면마다 다른 조건(기간 · 시간대 · 대상 범위)으로 계산되는지 확인합니다. 셋째, 지표 정의를 바꿀 때 누가 승인했는지 기록이 남는지 확인합니다.

별도 도구를 들이지 않아도 PostgreSQL 뷰(View, 저장해 둔 조회문)나 공용 조회 함수 하나에 지표 정의를 모으는 것부터 시작할 수 있습니다. 사람이 검토한 뒤 결과를 내보내는 서비스라면, 결과와 함께 어느 지표 정의를 썼는지 보이는 것이 Snowflake 예시와 같은 방향입니다.

## 5. 흔한 함정

첫째, 정의만 모으고 소유자와 승인 절차를 두지 않으면 같은 이름에 다른 의미가 다시 섞입니다. Snowflake 가 개념마다 소속 도메인과 스튜어드(Steward, 승인 담당자)를 두는 이유가 여기에 있습니다.

둘째, 의미 저장과 계산 실행을 한 계층에 모두 맡기려 하면 역할이 흐려집니다. Snowflake 는 온톨로지가 수식을 실행하지 않고 계산은 Semantic View 가 맡도록 나눴습니다.

셋째, 정의를 바꾸면 모든 곳에 바로 반영되므로 검토 없이 바꾸면 과거 보고서와 숫자가 달라집니다. 정의 변경은 초안과 승인 단계를 거치게 하는 편이 안전합니다.

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 시맨틱 레이어(Semantic Layer) | 원천 테이블과 화면 사이에서 업무 용어와 지표의 정의를 한 곳에 모아 두는 계층입니다. |
| 지표(Metric) | 매출 · 객단가처럼 원천 값을 집계해 업무 판단에 쓰는 숫자입니다. |
| BI 도구(Business Intelligence) | 데이터를 불러와 대시보드와 보고서를 만드는 도구입니다. Tableau · Looker 가 대표적입니다. |
| dbt | 데이터 웨어하우스 안의 데이터를 SQL 로 가공 · 관리하는 오픈소스 도구로, dbt Semantic Layer 는 그 위에서 지표를 정의하는 기능입니다. |
| 데이터 웨어하우스(Data Warehouse) | 여러 원천의 데이터를 분석용으로 모아 둔 저장소입니다. Snowflake 가 대표적인 클라우드 제품입니다. |
| MetricFlow | dbt Semantic Layer 에서 지표 정의를 읽고 요청에 맞는 조인과 집계를 처리하는 엔진입니다. |
| 온톨로지(Ontology) | 어떤 분야의 개념과 개념 사이 관계를 정해 둔 체계로, 여기서는 업무 용어의 승인된 의미를 담습니다. |
| 도메인 스튜어드(Domain Steward) | 한 업무 영역의 용어와 지표 정의를 승인하고 관리하는 담당자입니다. |
