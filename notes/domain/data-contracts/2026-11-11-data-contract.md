# 데이터 계약(Data Contract) — 데이터를 넘기는 쪽과 받는 쪽의 약속

> 분류: 도메인 › 데이터 계약 · 작성: 2026-11-11 · 실린 노트: [2026-11-11](../../../daily/2026-11-11.md) · [전체 색인](../../../README.md)

**한 줄 정의**: 데이터를 만드는 쪽이 그 데이터를 쓰는 쪽에게 컬럼 이름 · 자료형 · 품질 · 갱신 주기 · 책임자 같은 조건을 문서로 약속하고, 그 약속을 기계가 검사하게 하는 방식입니다.

**그날 소식과 연결**: 이번 회차 Databricks 소식은 지표 정의를 한 곳에 두고 BI 도구로 한 방향으로만 내보내는 구조여서, 받는 쪽이 기대할 수 있는 모양을 약속한다는 점에서 데이터 계약과 이어집니다.

## 1. 왜 필요한가

주문 서비스를 맡은 팀이 orders 테이블의 amount 컬럼 이름을 total_amount 로 바꿨다고 가정합니다. 서비스 코드와 API 시험은 모두 통과하므로 배포는 문제없이 끝납니다. 그런데 이 테이블을 매일 밤 읽어 매출 집계를 만드는 다른 팀의 정기 작업은 다음 날 새벽에 실패합니다.

데이터를 넘기는 쪽은 누가 이 컬럼을 읽는지 모르고, 받는 쪽은 언제 무엇이 바뀔지 모릅니다. API 에는 명세와 버전이 있지만, 테이블이나 이벤트로 넘기는 데이터에는 그런 약속이 없는 경우가 많습니다. 데이터 계약(Data Contract)은 이 빈자리를 API 명세와 같은 방식으로 채우려는 개념입니다.

## 2. 동작 원리

데이터 계약은 보통 세 부분으로 이루어집니다. 첫째는 약속의 내용입니다. 컬럼 이름 · 자료형 · 빈 값 허용 여부 같은 스키마(Schema, 데이터의 구조 정의)와 품질 조건 · 갱신 주기 · 책임자를 적습니다. ODCS(Open Data Contract Standard, 데이터 계약을 YAML 로 적는 공개 표준)는 이 내용을 스키마 · 데이터 품질 · 서비스 수준 약속(Service-Level Agreement) · 팀 · 지원 채널 같은 절로 나눕니다.

둘째는 검사입니다. 약속을 문서로만 두면 지켜지지 않으므로, 데이터를 만드는 단계에서 기계가 계약과 실제 결과를 비교합니다. dbt(SQL 로 데이터 웨어하우스 안의 데이터를 가공 · 관리하는 오픈소스 도구)의 모델 계약(Model Contract)은 빌드 전에 쿼리 결과의 컬럼 이름과 자료형이 계약과 맞는지 확인하고, 맞지 않으면 빌드를 실패시킵니다.

셋째는 변경 절차입니다. dbt 는 이전 상태와 비교해 컬럼 삭제 · 자료형 변경 · 제약 조건 삭제나 수정을 깨지는 변경(Breaking Change)으로 보고 오류를 냅니다. dbt 문서는 이런 변경을 다루는 방법으로 모델 버전(Model Version) 기능을 안내합니다.

## 3. 예시 장면

아래는 설명을 위한 가상 장면입니다. 숙소 예약 서비스의 예약 팀은 reservations 테이블을 만들고, 정산 팀은 그 테이블을 읽어 일별 정산 집계를 만듭니다.

월요일에 두 팀은 reservations 의 계약을 정합니다. 계약에는 reservation_id 는 비어 있으면 안 되고, price 는 정수이며, 매일 새벽 2시 전에 전날 데이터가 채워진다는 조건이 들어갑니다. 책임자 칸에는 예약 팀이 적힙니다.

수요일에 예약 팀 개발자가 price 를 소수점 금액으로 바꾸는 변경을 올립니다. 배포 전 검사가 계약의 자료형과 다르다는 이유로 실패하고, 개발자는 정산 팀과 먼저 이야기해야 한다는 것을 그 자리에서 알게 됩니다.

두 팀은 새 컬럼 price_decimal 을 추가하고 기존 price 를 한 달 동안 유지하기로 합니다. 정산 집계는 그 사이에 새 컬럼으로 옮겨 가고, 새벽 정기 작업은 한 번도 실패하지 않습니다.

## 4. 실무에서 확인할 점

첫째, 서비스 DB 테이블을 다른 팀의 정기 작업이나 분석 쿼리가 직접 읽고 있는지 확인합니다. 직접 읽는 곳이 있다면 그 테이블은 이미 약속 없이 공개된 API 와 같습니다.

둘째, 스키마를 바꾸는 마이그레이션(Migration, DB 구조 변경 스크립트)을 검토할 때 컬럼 삭제 · 이름 변경 · 자료형 변경을 따로 표시하는 규칙이 있는지 확인합니다. dbt 문서의 표는 Postgres 에서 not_null · primary_key · foreign_key · unique · check 다섯 제약이 모두 정의되고 강제된다고 적으므로, PostgreSQL 을 쓰는 서비스라면 계약의 제약을 DB 제약으로 그대로 옮길 수 있습니다.

셋째, 서버 여러 대와 여러 팀이 함께 읽는 이벤트나 정기 작업 결과 테이블은 책임자 · 갱신 주기 · 늦게 도착했을 때 알릴 곳을 한 문서에 적어 둡니다. 별도 도구 없이도 ODCS 형식의 YAML 파일 하나를 코드 저장소에 두고 코드 검토 대상에 넣는 것부터 시작할 수 있습니다.

```yaml
models:
  - name: dim_customers
    config:
      contract:
        enforced: true
    columns:
      - name: customer_id
        data_type: int
        constraints:
          - type: not_null
      - name: customer_name
        data_type: string
```

_dbt 문서 'Model contracts' 의 계약 설정 예시를 줄여 옮겼습니다._

## 5. 흔한 함정

첫째, 계약을 문서로만 쓰고 검사에 연결하지 않으면 몇 달 뒤 실제 테이블과 문서가 달라집니다. 빌드나 배포 단계에서 기계가 약속을 확인해야 계약이 계속 유효합니다.

둘째, 데이터 플랫폼마다 제약 조건을 강제하는 범위가 다릅니다. dbt 문서에 따르면 Snowflake(클라우드 데이터 웨어하우스)와 Redshift(AWS 의 데이터 웨어하우스)는 not_null 만 강제하고 primary_key · foreign_key · unique 는 정의만 받고 강제하지 않습니다. 계약에 unique 를 적었다고 중복이 막힌다고 믿으면 중복 행이 그대로 쌓입니다.

셋째, 모든 테이블에 계약을 걸면 작은 변경마다 검토가 필요해 개발 속도가 떨어집니다. 다른 팀이나 외부 시스템이 읽는 데이터처럼 팀 경계를 넘는 데이터부터 계약을 거는 편이 부담이 적습니다.

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 데이터 계약(Data Contract) | 데이터를 만드는 쪽이 쓰는 쪽에게 구조 · 품질 · 갱신 주기 · 책임자를 문서로 약속하고 기계로 검사하는 방식입니다. |
| 스키마(Schema) | 컬럼 이름 · 자료형 · 빈 값 허용 여부처럼 데이터의 구조를 정한 정의입니다. |
| 깨지는 변경(Breaking Change) | 컬럼 삭제나 자료형 변경처럼 기존 소비자가 고치지 않으면 실패하게 되는 변경입니다. |
| 모델 계약(Model Contract) | dbt 에서 모델 결과의 컬럼 이름 · 자료형 · 제약을 약속하고, 맞지 않으면 빌드를 실패시키는 설정입니다. |
| ODCS(Open Data Contract Standard) | Bitol 프로젝트가 공개한, 데이터 계약을 YAML 파일로 적는 표준입니다. |
| 서비스 수준 약속(Service-Level Agreement) | 갱신 주기 · 가용성처럼 데이터나 서비스가 지켜야 할 수준을 정한 약속으로, 흔히 SLA 라고 줄여 씁니다. |
| 마이그레이션(Migration) | DB 의 테이블 · 컬럼 구조를 바꾸는 스크립트와 그 적용 과정입니다. |
