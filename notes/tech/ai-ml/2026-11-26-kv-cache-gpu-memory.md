# KV 캐시(KV Cache): 문맥이 길어질수록 GPU 메모리가 줄어드는 이유

> 분류: 기술 › AI·머신러닝 · 작성: 2026-11-26 · 실린 노트: [2026-11-26](../../../daily/2026-11-26.md) · [전체 색인](../../../README.md)

**한 줄 정의**: 언어 모델이 앞 토큰의 키(Key)와 값(Value) 계산 결과를 저장해 다음 토큰을 빠르게 만드는 대신, 문맥 길이와 동시 요청 수에 비례해 GPU 메모리를 차지하는 저장 공간입니다.

## 1. 왜 필요한가

언어 모델은 답을 한 번에 만들지 않고 토큰(Token, 모델이 글을 나누어 처리하는 단위)을 하나씩 이어 붙여 만듭니다.

새 토큰 하나를 만들 때마다 모델은 지금까지 나온 모든 토큰을 다시 참고해야 합니다.

앞 토큰의 계산 결과를 버리면 답이 길어질수록 같은 계산을 매번 되풀이하게 되고, 응답 시간이 길이에 따라 빠르게 늘어납니다.

KV 캐시(KV Cache)는 이 반복 계산을 피하려고 앞 토큰의 계산 결과를 GPU 메모리에 남겨 두는 장치입니다.

그 대가로 문맥이 길고 동시 요청이 많을수록 GPU 메모리가 빠르게 차고, 메모리가 모자라면 처리할 수 있는 요청 수가 줄어듭니다.

## 2. 동작 원리

트랜스포머(Transformer) 모델의 어텐션(Attention) 층은 토큰마다 질의(Query) · 키(Key) · 값(Value) 세 벡터를 만들고, 새 토큰의 질의를 앞 토큰들의 키와 비교해 값을 섞습니다.

앞 토큰의 키와 값은 한 번 계산하면 바뀌지 않으므로, 층마다 저장해 두고 새 토큰의 키와 값만 덧붙이면 됩니다.

요청 처리는 두 단계로 나뉩니다: 입력 프롬프트 전체를 한 번에 계산해 캐시를 채우는 프리필(Prefill) 단계와, 토큰을 하나씩 만들며 캐시를 늘리는 디코드(Decode) 단계입니다.

토큰 하나가 차지하는 크기는 '2(키와 값) × 층 수 × 키·값 헤드 수 × 헤드 차원 × 원소 하나의 바이트 수'입니다.

예시 수치로 층 32개 · 키·값 헤드 8개 · 헤드 차원 128 · 16비트(2바이트) 모델이면 토큰 하나에 128KiB 이고, 8,000토큰 문맥 하나에 약 1GiB 가 필요합니다.

같은 예시에서 키·값 헤드가 32개라면 토큰 하나에 512KiB 로 네 배가 되며, 그룹 질의 어텐션(GQA, Grouped-Query Attention)은 여러 질의 헤드가 키·값 헤드를 함께 쓰게 해 이 크기를 줄입니다.

## 3. 예시 장면

가상의 쇼핑몰이 상품 문의 챗봇을 GPU 한 장에 모델을 직접 띄워 운영한다고 가정합니다(이하 수치는 모두 예시입니다).

모델 가중치가 GPU 메모리의 절반을 차지하고, 나머지 약 20GiB 가 KV 캐시 공간으로 남습니다.

평소에는 대화 하나가 2,000토큰 안팎이라 동시에 수십 개의 대화를 처리해도 공간이 남습니다.

할인 행사 날 고객들이 긴 주문 내역을 통째로 붙여 넣으면서 대화 하나가 10,000토큰을 넘기 시작하고, 같은 공간에 들어가는 대화 수가 다섯 분의 일로 줄어듭니다.

서빙 엔진은 공간이 모자라자 진행 중인 요청 일부를 멈추고 캐시를 비웠다가 나중에 다시 계산하며, 사용자는 첫 글자가 나오기까지 오래 기다리게 됩니다.

vLLM 논문은 기존 서빙 시스템이 요청마다 최대 길이만큼 연속 메모리를 미리 잡아 단편화와 중복 할당으로 KV 캐시 메모리를 낭비한다고 지적하고, 운영체제의 페이징(Paging)처럼 작은 단위로 나누어 저장하는 PagedAttention 으로 같은 지연 시간에서 처리량을 2~4배 높였다고 보고합니다.

## 4. 실무에서 확인할 점

모델을 직접 띄우는 서비스라면 모델 설정 파일의 층 수 · 키·값 헤드 수 · 헤드 차원으로 토큰 하나의 KV 캐시 크기를 먼저 계산하고, 최대 문맥 길이와 목표 동시 요청 수를 곱해 GPU 메모리에 들어가는지 확인합니다.

vLLM 을 쓴다면 문서가 안내하는 대로 로그에 'not enough KV cache space' 로 시작하는 선점(Preemption) 경고가 나오는지 보고, 잦으면 gpu_memory_utilization 을 높이거나 max_num_seqs · max_num_batched_tokens 를 줄여 봅니다.

AI API 를 호출하는 서비스라면 KV 캐시 비용이 입력 토큰 요금과 첫 토큰까지의 지연에 들어 있으므로, 요청마다 붙이는 시스템 프롬프트와 대화 이력의 길이를 지표로 남깁니다.

같은 앞부분 프롬프트를 여러 요청이 공유한다면 그 계산 결과를 재사용하는 프롬프트 캐싱(Prompt Caching) 기능이 있는지 확인하고, 앞부분 문구가 요청마다 바뀌지 않게 둡니다.

서버 여러 대가 같은 모델을 띄운다면 GPU 사용률이 아니라 KV 캐시 사용률과 대기 중인 요청 수를 기준으로 부하를 나눕니다.

## 5. 흔한 함정

모델 가중치 크기만 보고 GPU 를 고르면, 실제 트래픽에서 KV 캐시 공간이 모자라 동시 처리 수가 기대보다 크게 줄어듭니다.

최대 문맥 길이를 모델이 허용하는 최댓값으로 열어 두면, 드물게 들어오는 아주 긴 요청 몇 개가 공간을 차지해 다른 요청이 선점되거나 대기합니다.

대화 이력을 자르지 않고 계속 붙여 보내면, AI API 를 쓰는 경우 입력 토큰 요금과 응답 지연이 대화가 길어질수록 함께 늘어납니다.

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 토큰(Token) | 모델이 글을 나누어 처리하는 단위이며, 한 단어가 여러 토큰으로 나뉘기도 합니다. |
| 어텐션(Attention) | 새 토큰이 앞 토큰들 가운데 어느 것을 얼마나 참고할지 계산하는 트랜스포머의 핵심 층입니다. |
| 프리필(Prefill) | 입력 프롬프트 전체를 한 번에 계산해 KV 캐시를 채우는 단계이며, 첫 토큰이 나오기까지의 지연을 좌우합니다. |
| 디코드(Decode) | 토큰을 하나씩 만들며 KV 캐시를 한 칸씩 늘려 가는 단계입니다. |
| 그룹 질의 어텐션(GQA, Grouped-Query Attention) | 여러 질의 헤드가 키·값 헤드 하나를 함께 써서 키·값 헤드 수를 줄이는 어텐션 방식입니다. |
| 선점(Preemption) | KV 캐시 공간이 모자랄 때 서빙 엔진이 진행 중인 요청을 멈추고 공간을 비우는 동작입니다. |
| vLLM | PagedAttention 으로 KV 캐시를 작은 블록 단위로 관리하는 오픈소스 언어 모델 서빙 엔진입니다. |
