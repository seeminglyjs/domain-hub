# 펜싱 토큰(Fencing Token) — 락이 만료된 뒤 늦게 도착한 쓰기 막기

> 분류: 기술 › 아키텍처 · 작성: 2026-11-12 · 실린 노트: [2026-11-12](../../../daily/2026-11-12.md) · [전체 색인](../../../README.md)

**한 줄 정의**: 락을 내줄 때마다 이전보다 큰 번호를 함께 내주고, 쓰기를 받는 저장소가 이미 본 번호보다 작은 번호의 쓰기를 거절하게 해서, 락이 만료된 줄 모르는 옛 소유자의 쓰기를 막는 방법입니다.

**그날 소식과 연결**: 이번 회차 Cloudflare 글은 느린 리더를 죽은 리더로 잘못 판단하는 문제를 합의 알고리즘 쪽에서 다루며, 펜싱 토큰은 같은 문제를 쓰기를 받는 저장소 쪽에서 막는 방법입니다.

## 1. 왜 필요한가

서버 세 대가 같은 정기 작업을 함께 돌리는 서비스에서, 한 번에 한 대만 작업하도록 분산 락(Distributed Lock)을 건다고 가정합니다. 락에는 서버가 죽어도 영원히 잠기지 않도록 만료 시간을 붙이며, 이렇게 기한이 정해진 락을 리스(Lease)라고 부릅니다. 문제는 락을 쥔 서버가 죽은 것이 아니라 잠깐 멈춘 경우에 생깁니다.

가비지 컬렉션(Garbage Collection, 쓰지 않는 메모리를 회수하는 작업)의 일시 정지나 네트워크 지연으로 서버가 멈춘 사이 락이 만료되면, 다른 서버가 락을 얻어 같은 데이터를 씁니다. 멈췄던 서버는 깨어난 뒤에도 자신이 락을 쥐고 있다고 믿고 쓰기를 이어 갑니다. Martin Kleppmann(분산 시스템 연구자, 『데이터 중심 애플리케이션 설계』 저자)은 쓰기 직전에 만료를 확인해도 확인과 쓰기 사이에 멈출 수 있어 이 문제가 풀리지 않는다고 설명합니다.

락을 쥔 쪽의 판단만으로는 '내가 아직 주인인가'를 보장할 수 없습니다. 펜싱 토큰(Fencing Token)은 이 판단을 쓰기를 받는 저장소 쪽으로 옮기는 방법입니다.

## 2. 동작 원리

펜싱 토큰은 세 단계로 동작합니다. 첫째, 락 서비스는 락을 내줄 때마다 이전보다 큰 번호를 함께 내줍니다. 둘째, 락을 얻은 쪽은 저장소에 쓸 때마다 이 번호를 함께 보냅니다. 셋째, 저장소는 지금까지 처리한 가장 큰 번호를 기억하고, 그보다 작은 번호가 붙은 쓰기를 거절합니다.

Kleppmann 의 예시에서 클라이언트 1 은 33번, 클라이언트 2 는 34번 토큰을 받습니다. 클라이언트 2 의 34번 쓰기가 먼저 처리되면, 늦게 도착한 클라이언트 1 의 33번 쓰기는 저장소가 거절합니다.

번호는 반드시 단조 증가(Monotonically Increasing, 줄지 않고 늘기만 함)해야 합니다. ZooKeeper(분산 시스템의 설정 · 락 · 리더 선출을 맡는 Apache 오픈소스 조정 서비스)는 순차 노드(Sequential Node)를 만들 때 이전보다 큰 번호를 붙이며, Kleppmann 은 ZooKeeper 의 zxid(변경마다 붙는 트랜잭션 번호)나 노드 버전을 토큰으로 쓸 수 있다고 적습니다.

Kleppmann 은 Redis 여러 대에 동시에 락을 거는 Redlock 알고리즘에는 이런 번호를 만드는 수단이 없다고 지적합니다. 그는 여러 노드가 어긋나지 않는 번호를 만들려면 합의 알고리즘(Consensus Algorithm, 여러 서버가 하나의 값에 동의하게 하는 절차)이 필요할 것이라고 봅니다.

## 3. 예시 장면

아래는 설명을 위한 가상 장면이며, 수치는 모두 예시 수치입니다. 배달 앱의 서버 A · B 는 매일 01:00 에 가맹 음식점별 정산 결과를 settlements 테이블에 기록하는 정기 작업을 함께 돌립니다.

01:00:00 에 서버 A 가 만료 30초짜리 락과 토큰 101 을 얻고 정산 계산을 시작합니다. 01:00:10 에 서버 A 는 긴 가비지 컬렉션 정지에 들어가 40초 동안 멈춥니다.

01:00:30 에 락이 만료되고, 서버 B 가 토큰 102 를 받아 최신 주문까지 반영한 정산 결과를 기록합니다. settlements 의 마지막 토큰 칸에는 102 가 저장됩니다.

01:00:50 에 깨어난 서버 A 는 멈추기 전 기준으로 계산한 결과를 토큰 101 과 함께 쓰려고 합니다. 저장소가 이미 102 를 보았으므로 이 쓰기는 거절되고, 서버 A 는 작업을 중단하고 경고 로그를 남깁니다. 토큰이 없었다면 오래된 정산 결과가 최신 결과를 덮어썼을 것입니다.

## 4. 실무에서 확인할 점

Spring 정기 작업을 서버 여러 대에서 돌리며 ShedLock(정기 작업이 여러 서버에서 겹쳐 돌지 않게 DB · Redis 등에 락을 거는 Java 라이브러리)을 쓰는 서비스라면, lockAtMostFor(락을 쥘 수 있는 최대 시간)가 실제 최대 실행 시간보다 충분히 긴지 확인합니다. ShedLock 문서는 작업이 이 시간보다 오래 돌면 락이 풀려 다른 노드가 락을 얻을 수 있고, 그 결과를 예측할 수 없다고 적습니다. 문서는 ShedLock 이 스케줄러가 아니라 락일 뿐이라고도 밝히므로, 늦게 도착한 쓰기를 막는 일은 따로 설계해야 합니다.

PostgreSQL 에 결과를 쓰는 작업이라면 대상 행에 마지막 토큰 컬럼을 두고, 받은 토큰이 더 클 때만 갱신하는 조건부 UPDATE 로 검사할 수 있습니다. 갱신된 행 수가 0 이면 다른 서버가 이미 더 새 토큰으로 썼다는 뜻이므로 작업을 멈춥니다.

토큰은 락을 얻는 동작과 같은 UPDATE 안에서 락 행의 번호를 1 올려 돌려받는 식으로, 락과 한 번에 받아야 합니다. 락과 번호를 따로 받으면 그 사이에 멈춘 서버가 더 큰 번호를 받을 수 있습니다.

Kleppmann 은 Redis 단일 노드 락이 중복 작업을 줄이는 효율 목적에는 충분하다고 봅니다. 데이터가 틀어지면 안 되는 정확성 목적이라면 락의 종류와 상관없이 저장소가 토큰을 검사하는지 확인합니다.

## 5. 흔한 함정

첫째, 쓰기 직전에 락 만료를 확인하는 것으로 충분하다고 믿는 경우입니다. 확인과 쓰기 사이에 멈춤이 끼어들 수 있으므로, 오래된 쓰기가 그대로 저장소에 도착합니다.

둘째, UUID 같은 무작위 값을 토큰으로 쓰는 경우입니다. 무작위 값은 크기로 순서를 비교할 수 없어, 저장소가 어느 쪽이 새 소유자인지 가릴 수 없습니다. Kleppmann 이 Redlock 의 무작위 값을 토큰으로 쓸 수 없다고 본 이유도 같습니다.

셋째, 토큰을 받아 두기만 하고 저장소가 검사하지 않는 경우입니다. 결과를 DB · 캐시 · 외부 API 여러 곳에 쓰는 작업이라면 검사하지 않는 한 곳에서 오래된 값이 그대로 덮어씁니다. 외부 결제 API 처럼 토큰을 검사할 수 없는 곳에는 멱등 키(Idempotency Key, 같은 요청을 여러 번 보내도 한 번만 처리되게 하는 식별자) 같은 다른 장치가 필요합니다.

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 펜싱 토큰(Fencing Token) | 락을 내줄 때마다 커지는 번호로, 저장소가 이미 본 번호보다 작은 번호의 쓰기를 거절하는 데 씁니다. |
| 분산 락(Distributed Lock) | 여러 서버 가운데 한 번에 하나만 어떤 작업을 하도록 공유 저장소에 거는 잠금입니다. |
| 리스(Lease) | 정해진 시간이 지나면 저절로 풀리는 락으로, 락을 쥔 서버가 죽어도 영원히 잠기지 않게 합니다. |
| 가비지 컬렉션(Garbage Collection) | JVM 같은 런타임이 쓰지 않는 메모리를 회수하는 작업으로, 이 동안 애플리케이션 스레드가 잠시 멈출 수 있습니다. |
| 단조 증가(Monotonically Increasing) | 값이 줄지 않고 늘기만 하는 성질로, 토큰의 앞뒤를 비교하려면 이 성질이 필요합니다. |
| 합의 알고리즘(Consensus Algorithm) | 일부 서버가 죽거나 끊겨도 여러 서버가 같은 값에 동의하게 하는 절차로, Raft · Paxos 가 대표적입니다. |
| ZooKeeper | 분산 시스템의 설정 · 락 · 리더 선출을 맡는 Apache 오픈소스 조정 서비스입니다. |
| ShedLock | 정기 작업이 여러 서버에서 겹쳐 돌지 않도록 DB · Redis 등에 락을 거는 Java 라이브러리입니다. |
