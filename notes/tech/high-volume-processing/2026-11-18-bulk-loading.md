# 대량 적재(Bulk Loading) — PostgreSQL 에 수백만 행을 빠르게 넣기

> 분류: 기술 › 대용량 처리 · 작성: 2026-11-18 · 실린 노트: [2026-11-18](../../../daily/2026-11-18.md) · [전체 색인](../../../README.md)

**한 줄 정의**: 많은 행을 DB 에 한꺼번에 넣을 때 행마다 INSERT 와 커밋을 반복하지 않고, COPY 같은 전용 명령을 쓰고 커밋 · 인덱스 · 제약 조건 · 통계 처리 순서를 바꿔 쓰기 비용을 줄이는 방법입니다.

**그날 소식과 연결**: 이번 회차 pg_fastload 1.0.0 은 COPY 보다 빠르다고 밝힌 병렬 적재 도구이며, 이 글은 그 비교 기준인 COPY 와 PostgreSQL 문서가 권하는 대량 적재 절차를 다룹니다.

## 1. 왜 필요한가

쇼핑몰이 매일 새벽 협력 업체에게서 상품 300만 개의 가격 파일을 받아 가격 테이블에 넣는다고 가정합니다(예시 수치). 정기 작업이 파일을 한 줄씩 읽어 행마다 INSERT 를 보내고, 자동 커밋이 켜져 있어 행마다 커밋까지 합니다. PostgreSQL 문서는 행마다 따로 커밋하면 PostgreSQL 이 행마다 많은 일을 하게 된다고 적습니다.

작업이 몇 시간씩 걸리면 아침 트래픽이 들어올 때까지 적재가 끝나지 않고, 같은 테이블을 읽는 API 가 덜 갱신된 가격을 보여 줍니다. 쓰기가 몰리는 동안 체크포인트가 잦아지고 디스크 쓰기가 늘어 다른 질의도 느려집니다. 대량 적재(Bulk Loading)는 많은 행을 한꺼번에 넣을 때 행 단위로 반복되는 비용을 줄이는 방법 모음입니다.

## 2. 동작 원리

첫째는 커밋을 묶는 것입니다. 자동 커밋(Autocommit)을 끄고 처음에 BEGIN, 끝에 COMMIT 을 한 번만 보내면 행마다 반복되던 커밋 비용이 사라집니다. 한 트랜잭션으로 넣으면 중간에 실패해도 앞의 행이 모두 롤백되어, 반만 들어간 상태가 남지 않습니다.

둘째는 COPY 명령입니다. COPY 는 여러 행을 한 명령으로 넣는 PostgreSQL 전용 명령으로, 문서는 INSERT 보다 유연성은 낮지만 오버헤드가 훨씬 적다고 설명합니다. 문서는 준비된 문장(Prepared Statement)과 배치 트랜잭션을 써도 COPY 가 거의 항상 더 빠르다고 적고, COPY 를 쓸 수 없을 때만 PREPARE 와 EXECUTE 반복을 권합니다.

셋째는 인덱스와 외래 키를 나중에 만드는 것입니다. 이미 들어간 데이터로 인덱스를 한 번에 만드는 것이 행마다 인덱스를 갱신하는 것보다 빠릅니다. 외래 키가 있는 테이블은 행마다 서버의 대기 트리거 이벤트 목록에 항목이 쌓이므로, 수백만 행을 넣으면 메모리가 부족해 실패할 수도 있다고 문서는 경고합니다.

넷째는 WAL(Write-Ahead Log, 변경 기록 파일)과 체크포인트(Checkpoint, 메모리에서 바뀐 페이지를 디스크에 모두 기록하는 시점) 비용입니다. 대량 적재는 체크포인트를 평소 주기보다 자주 일으키므로, 문서는 적재 동안 max_wal_size 를 잠시 올려 체크포인트 수를 줄이라고 권합니다. 마지막으로 적재 뒤에는 ANALYZE 로 통계를 새로 모아야 질의 계획기가 바뀐 데이터 분포에 맞는 계획을 세웁니다.

2026-11-17 공개된 pg_fastload 는 같은 문제를 병렬 처리로 다룹니다. 파일 읽기 · 파싱 · 행 만들기를 여러 백그라운드 워커가 나눠 하고, 테이블에 넣는 단계만 하나로 남깁니다.

## 3. 예시 장면

아래는 설명을 위한 가상 장면이며, 시각과 수치는 모두 예시 수치입니다. 쇼핑몰의 가격 반영 작업은 인덱스가 없는 스테이징 테이블(Staging Table, 본 테이블에 넣기 전에 잠시 받아 두는 테이블) price_import 와 본 테이블 product_price 를 씁니다.

02:00 에 작업이 트랜잭션을 열고 price_import 를 TRUNCATE 한 뒤, 같은 트랜잭션에서 COPY price_import FROM STDIN 으로 파일 내용을 DB 연결을 통해 보냅니다. 300만 행이 한 명령으로 들어가고, 스테이징 테이블에는 인덱스가 없어 행마다 갱신할 인덱스도 없습니다.

02:03 에 작업은 price_import 에 ANALYZE 를 실행하고, 상품 ID 가 비었거나 가격이 음수인 행의 수를 조회합니다. 이 수가 정해 둔 기준보다 많으면 COMMIT 대신 ROLLBACK 하고 경고를 남기므로, 본 테이블은 어제 가격 그대로 남습니다.

검사를 통과하면 02:04 에 INSERT ... SELECT ... ON CONFLICT 문 하나로 price_import 의 값을 product_price 에 반영하고 커밋합니다. 행마다 INSERT 와 커밋을 반복하던 이전 방식에서는 같은 작업이 두 시간 넘게 걸렸다고 가정하면, 차이는 커밋 횟수와 명령 횟수에서 나옵니다.

## 4. 실무에서 확인할 점

첫째, Spring 정기 작업이 JPA 로 행마다 저장하고 있는지 확인합니다. 행마다 저장할 수밖에 없다면 JDBC 배치를 쓰고, PostgreSQL JDBC 드라이버(PgJDBC)의 reWriteBatchedInserts 설정을 검토합니다. PgJDBC 문서는 이 설정의 기본값이 false 이며, 켜면 배치 INSERT 를 여러 VALUES 를 묶은 INSERT 하나로 바꿔 2~3배 빨라진다고 적습니다.

둘째, COPY 를 쓴다면 파일 위치를 확인합니다. COPY 에 파일 이름을 적으면 애플리케이션 서버가 아니라 DB 서버가 그 파일을 읽고, 슈퍼유저나 pg_read_server_files 같은 역할이 있어야 합니다. 애플리케이션 서버에 있는 파일이라면 COPY ... FROM STDIN 으로 DB 연결을 통해 보내야 하며, PgJDBC 는 이를 위한 CopyManager API 를 제공합니다.

셋째, 서버를 여러 대 띄운다면 적재 작업이 한 서버에서만 돌도록 분산 락으로 막았는지 확인합니다. 두 서버가 같은 파일을 동시에 넣으면 행이 두 번 들어가거나 TRUNCATE 가 서로의 적재를 지웁니다.

넷째, 복제나 WAL 아카이빙을 쓰는 운영 DB 에서는 문서의 wal_level minimal 같은 설정 변경을 그대로 따르지 않습니다. 문서는 이 변경이 서버 재시작을 요구하고 이전 기본 백업을 복구에 쓸 수 없게 만든다고 적습니다. 대신 적재 시간대에 체크포인트가 너무 잦다는 경고가 로그에 남는지 보고 max_wal_size 를 조정할지 검토합니다.

## 5. 흔한 함정

첫째, 큰 적재를 한 트랜잭션으로 넣으면서 실패에 대비하지 않는 경우입니다. 문서에 따르면 COPY FROM 이 실패하면 이미 넣은 행은 보이지 않는 삭제 상태로 남아 디스크를 차지하므로, VACUUM 으로 공간을 회수해야 합니다. PostgreSQL 17 부터는 ON_ERROR ignore 옵션으로 형식이 잘못된 행을 버리고 계속 넣을 수 있지만, text · csv 형식에서만 쓸 수 있습니다.

둘째, 이미 서비스 중인 테이블에서 속도를 위해 인덱스를 지우는 경우입니다. 문서는 인덱스가 없는 동안 다른 사용자의 질의가 느려질 수 있고, 유니크 인덱스를 지우면 그동안 중복 검사도 사라진다고 경고합니다. 스테이징 테이블에 먼저 넣고 본 테이블에는 한 문장으로 반영하면 본 테이블의 인덱스를 건드리지 않아도 됩니다.

셋째, 적재 뒤에 ANALYZE 를 하지 않는 경우입니다. 통계가 옛 분포에 머물러 있으면 계획기가 실제와 다른 행 수를 가정해 나쁜 계획을 세울 수 있습니다. autovacuum 이 나중에 ANALYZE 를 해 줄 수 있지만, 적재 직후 바로 질의가 들어오는 작업이라면 직접 실행하는 편이 안전합니다.

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 대량 적재(Bulk Loading) | 많은 행을 DB 에 한꺼번에 넣는 작업과, 그때 행마다 반복되는 비용을 줄이는 방법입니다. |
| COPY | 파일이나 DB 연결로 받은 여러 행을 한 명령으로 테이블에 넣거나 꺼내는 PostgreSQL 전용 명령입니다. |
| 자동 커밋(Autocommit) | 문장 하나를 실행할 때마다 바로 커밋하는 동작으로, JDBC 연결의 기본값입니다. |
| 준비된 문장(Prepared Statement) | 한 번 파싱 · 계획한 문장을 값만 바꿔 여러 번 실행하는 방식입니다. |
| 체크포인트(Checkpoint) | 메모리에서 바뀐 데이터 페이지를 모두 디스크에 기록하는 시점으로, 잦아지면 디스크 쓰기가 늘어납니다. |
| 스테이징 테이블(Staging Table) | 원천 데이터를 본 테이블에 반영하기 전에 잠시 받아 두고 검사하는 테이블입니다. |
| ANALYZE | 테이블의 값 분포 통계를 새로 모아 질의 계획기가 알맞은 실행 계획을 고르게 하는 PostgreSQL 명령입니다. |
| pg_fastload | pg_bulkload 를 바탕으로 읽기 · 파싱 단계를 병렬로 나눈 PostgreSQL 대량 적재 오픈소스 도구입니다. |
