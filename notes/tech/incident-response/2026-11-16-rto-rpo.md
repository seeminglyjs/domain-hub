# 복구 시간 목표 · 복구 시점 목표(RTO · RPO, Recovery Time · Point Objective) — 얼마나 빨리, 어디까지 되살릴지 정하기

> 분류: 기술 › 장애 대응 · 작성: 2026-11-16 · 실린 노트: [2026-11-16](../../../daily/2026-11-16.md) · [전체 색인](../../../README.md)

**한 줄 정의**: 장애가 났을 때 서비스를 몇 시간 안에 다시 열어야 하는지(RTO)와 장애 직전 몇 분어치 데이터까지 잃어도 되는지(RPO)를 미리 정해, 백업 주기 · 복제 구성 · 예비 서버 규모를 고르는 기준으로 삼는 두 값입니다.

**그날 소식과 연결**: 이번 회차 Workday 장애는 재해 복구 환경을 점검하던 중 그 환경의 서비스가 운영 DB 에 연결되며 일어났으며, 이 글은 그 재해 복구 계획이 무엇을 목표로 세우는지 다룹니다.

## 1. 왜 필요한가

새벽 3시에 주문 DB 서버의 디스크가 고장 났다고 가정합니다. 담당자는 백업으로 되살릴 수 있다는 것만 알고, 서비스를 몇 시간 안에 다시 열어야 하는지와 몇 분어치 주문까지 잃어도 되는지는 정해 두지 않았습니다. 그러면 어젯밤 백업으로 바로 되살릴지, 오래 걸려도 장애 직전까지 되살릴지를 장애 한가운데서 정해야 합니다.

재해 복구(Disaster Recovery)는 서버 · 데이터센터 · 지역 단위의 큰 장애 뒤에 서비스와 데이터를 되살리는 계획입니다. 이 계획의 출발점이 복구 시간 목표(RTO, Recovery Time Objective)와 복구 시점 목표(RPO, Recovery Point Objective)입니다. 두 값이 없으면 백업 주기 · 복제 구성 · 예비 서버 규모를 무엇에 맞춰 정할지 기준이 없습니다.

## 2. 동작 원리

AWS(Amazon 의 클라우드 서비스) 재해 복구 백서는 RTO 를 서비스가 끊긴 때부터 다시 열릴 때까지 허용할 수 있는 최대 지연으로 정의합니다. RPO 는 마지막 복구 지점 이후 허용할 수 있는 최대 시간으로, 장애 직전 몇 분어치 데이터까지 잃어도 되는지를 뜻합니다. 백서는 두 값을 조직이 정한다고 적습니다.

RPO 는 백업과 복제 방식이 정합니다. 예시 수치로 하루 한 번 백업만 있으면 최대 약 24시간어치 데이터를 잃을 수 있고, 데이터를 계속 복제하면 그 간격이 훨씬 짧아집니다. RTO 는 복구할 곳에 무엇이 미리 준비되어 있는지가 정합니다.

백서는 복구 방식을 네 가지로 나눕니다. 백업 후 복원(Backup and Restore)은 가장 싸지만 인프라 · 설정 · 코드까지 다시 배포해야 합니다. 파일럿 라이트(Pilot Light)는 DB 같은 핵심 자원만 켜 두고 애플리케이션 서버는 장애 때 켜는 방식이며, 웜 스탠바이(Warm Standby)는 작은 규모로 계속 돌아가는 사본을 두고 장애 때 규모만 키우는 방식입니다. 멀티 사이트 액티브/액티브(Multi-site Active/Active)는 여러 지역이 동시에 요청을 받아 복구 시간을 0 에 가깝게 줄이지만 가장 비싸고 복잡합니다.

백서는 복구 방식의 비용이 장애로 잃는 비용보다 크면, 규제 같은 다른 이유가 없는 한 그 방식을 두지 말라고 적습니다. 또 데이터 손상이나 삭제에는 복제본도 함께 망가지므로, 액티브/액티브 구성이라도 그런 장애의 복구 시점은 0 보다 크다고 밝힙니다.

## 3. 예시 장면

아래는 설명을 위한 가상 장면이며, 시각과 수치는 모두 예시 수치입니다. 숙소 예약 서비스는 예약 DB 의 RPO 를 5분, RTO 를 1시간으로 정하고, 기본 백업은 매일 새벽 2시에 받으며 변경 기록은 계속 보관합니다.

14:20 에 한 개발자가 조건이 빠진 UPDATE 를 실행해 모든 예약의 상태가 취소로 바뀝니다. 복제 DB 에도 같은 변경이 몇 초 만에 넘어가므로, 복제본으로 전환하는 것으로는 되살릴 수 없습니다.

14:30 에 담당자는 새 서버에 새벽 2시 기본 백업을 풀고, 보관해 둔 변경 기록을 14:19 까지 재생하도록 복구 목표 시각을 지정합니다. 15:10 에 복구가 끝나고, 담당자는 예약 상태를 확인한 뒤 애플리케이션의 DB 연결을 새 서버로 바꿉니다.

이 장면에서 잃은 데이터는 14:19~14:20 사이 1분어치이며, 서비스가 멈춘 시간은 약 50분입니다. 두 값이 미리 정한 RPO 5분 · RTO 1시간 안에 들어오므로 계획대로 복구된 셈입니다.

2026-11-13 Workday(인사 · 재무 업무용 클라우드 소프트웨어 회사) 장애는 다른 쪽 위험을 보여 줍니다. 여러 대학 IT 부서가 옮겨 적은 Workday 공지에 따르면 재해 복구 사이트를 점검하던 중 그 사이트의 서비스가 운영 DB 에 연결되었고, 데이터가 서로 맞지 않는 상태가 되었습니다. 복구 환경이 운영 데이터에 닿을 수 있으면 복구를 준비하는 일 자체가 장애 원인이 될 수 있습니다.

## 4. 실무에서 확인할 점

PostgreSQL 을 직접 운영하는 서비스라면 RPO 는 연속 아카이빙(Continuous Archiving) 설정이 정합니다. PostgreSQL 문서는 기본 백업과 계속 보관한 WAL(Write-Ahead Log, 변경 기록 파일)을 합쳐 원하는 시각까지 되돌리는 시점 복구(PITR, Point-in-Time Recovery)를 설명합니다. 이를 위해 wal_level 을 replica 이상으로, archive_mode 를 on 으로 두고 archive_command 나 archive_library 로 WAL 을 다른 곳에 복사합니다.

문서는 archive_command 가 성공했을 때만 0 을 돌려줘야 한다고 강조합니다. 0 을 받으면 PostgreSQL 은 보관이 끝났다고 보고 그 WAL 을 지우거나 다시 쓰기 때문입니다. 문서는 pg_dump 로 만든 덤프로는 이 방식을 쓸 수 없고, 아카이빙이 밀리지 않는지 감시하라고도 적습니다.

RTO 는 실제로 복원해 봐야 알 수 있습니다. 기본 백업 크기와 재생할 WAL 양에 따라 복원 시간이 달라지므로, 정기적으로 다른 서버에 복원해 걸린 시간을 재고 그 값을 RTO 와 비교합니다. 클라우드 관리형 DB 를 쓴다면 자동 백업 보존 기간과 시점 복원 기능의 범위가 RPO 에 맞는지 확인합니다.

서버 여러 대와 Redis(메모리 기반 키-값 저장소) 같은 공유 캐시를 쓰는 서비스라면, DB 를 되살린 뒤 캐시에 남은 옛 값과 정기 작업이 만든 집계 테이블을 어떻게 다시 맞출지도 절차에 넣습니다. 복구용 서버의 설정 파일이 운영 DB 주소를 가리키지 않는지, 복구 환경의 계정이 운영 DB 에 쓸 권한이 없는지도 확인합니다.

```
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f'

restore_command = 'cp /mnt/server/archivedir/%f %p'
```

*PostgreSQL 문서 'Continuous Archiving and Point-in-Time Recovery (PITR)' 의 보관 설정과 복구 설정 예시를 모아 옮겼습니다.*

## 5. 흔한 함정

첫째, 복제본이 있으니 백업이 필요 없다고 믿는 경우입니다. AWS 백서는 계속 복제하는 방식이 데이터 손상이나 악의적인 삭제에서는 시점 백업만큼 보호하지 못할 수 있다고 적습니다. 잘못 실행한 UPDATE 는 복제본에도 그대로 넘어갑니다.

둘째, 백업을 받기만 하고 복원해 보지 않는 경우입니다. AWS 백서는 자주 시험한 복구 경로만 실제로 동작한다고 적고, 드물게 실행하는 복구 경로를 피해야 할 모양으로 듭니다. 처음 복원하는 날이 장애 날이면 RTO 를 지킬 수 없습니다.

셋째, 복구 환경을 운영 환경과 같은 설정 · 계정으로 만들어 두는 경우입니다. 복구 훈련이나 점검 중에 복구 환경이 운영 DB 에 쓰면, Workday 사례처럼 장애를 대비하던 준비가 데이터를 어긋나게 만듭니다. AWS 백서도 지역마다 다른 계정을 써서 자원과 보안을 가장 높은 수준으로 격리하라고 권합니다.

## 용어 풀이

| 용어 | 뜻 |
|---|---|
| 재해 복구(Disaster Recovery) | 서버 · 데이터센터 · 지역 단위의 큰 장애 뒤에 서비스와 데이터를 되살리는 계획과 절차입니다. |
| 복구 시간 목표(Recovery Time Objective) | RTO 라고 줄여 쓰며, 서비스가 끊긴 때부터 다시 열릴 때까지 허용할 수 있는 최대 시간입니다. |
| 복구 시점 목표(Recovery Point Objective) | RPO 라고 줄여 쓰며, 마지막 복구 지점 이후 잃어도 되는 데이터의 최대 시간 범위입니다. |
| 시점 복구(Point-in-Time Recovery) | PITR 이라고 줄여 쓰며, 기본 백업에 변경 기록을 원하는 시각까지 재생해 그 시각의 상태로 되돌리는 복구 방식입니다. |
| WAL(Write-Ahead Log) | PostgreSQL 이 데이터 파일을 바꾸기 전에 변경 내용을 먼저 적어 두는 기록 파일로, 계속 보관하면 시점 복구에 씁니다. |
| 파일럿 라이트(Pilot Light) | DB 같은 핵심 자원만 복구 지역에 켜 두고, 애플리케이션 서버는 장애 때 켜는 재해 복구 방식입니다. |
| 웜 스탠바이(Warm Standby) | 작은 규모로 계속 돌아가는 사본을 복구 지역에 두고, 장애 때 규모만 키우는 재해 복구 방식입니다. |
