## 도메인 소식

### 1. Snowflake 가 업무 용어의 승인된 의미를 관리하는 Business Ontology 를 발표했습니다.

`제품` · 2026-11-03

Snowflake(클라우드 데이터 웨어하우스 회사)는 2026-11-03 자사 행사 Expedition 2026 에서 Horizon Context(Snowflake 안에서 승인된 업무 맥락을 모아 두는 기능)의 새 기능인 Business Ontology 를 발표했습니다. AI 에이전트가 순매출 같은 업무 용어를 제멋대로 해석하지 않도록, 사람이 승인한 정의만 에이전트에 주려는 것이 배경입니다.

Business Ontology 는 용어 · 지표 · 정책 같은 개념을 그래프로 연결하고, 각 개념을 실제 테이블과 뷰에 연결합니다. 새 개념은 초안으로 시작하고, 승인된 개념을 고치면 도메인 스튜어드(Domain Steward, 그 업무 영역의 승인 담당자)가 수락할 때까지 에이전트는 기존 버전을 씁니다.

온톨로지(Ontology, 개념과 관계를 정해 둔 체계)는 의미만 저장하고 계산은 Semantic View(지표의 조인 · 집계를 계산하는 Snowflake 기능)가 맡으며, 모든 변경은 기록으로 남습니다. 보도자료 기준으로 Business Ontology 는 공개 프리뷰 예정 상태이고, 엔지니어링 블로그는 비공개 프리뷰 단계라고 적습니다.

> 확인할 점: 지표 정의가 어디에 있고 누가 바꾸는지 정리할 때, 의미 · 계산 · 승인을 나누는 이 구조를 비교 기준으로 쓸 수 있습니다.

## 기술 소식

### 1. Next.js 가 16.4.5 · 15.5.29 에서 캐시 관련 정보 노출 등 취약점 7건을 고쳤습니다.

`프론트` · 2026-11-03

Next.js 는 2026-11-03 정기 보안 릴리스로 16.4.5(Active LTS, 현재 장기 지원판)와 15.5.29(Maintenance LTS, 보안 수정만 받는 장기 지원판)를 냈습니다. 일주일 전 사전 공지로 팀들이 업그레이드를 미리 계획하게 한 회차입니다.

가장 심각한 것(High)은 Cache Components(Next.js 의 컴포넌트 단위 캐시 기능)에서 unstable_cache 와 use cache(둘 다 Next.js 의 캐시 API)를 함께 쓸 때, 캐시가 비어 있는 동안 동시에 들어온 호출이 다른 테넌트(Tenant, 한 서비스를 함께 쓰는 고객 단위)의 결과를 받을 수 있는 문제입니다. 나머지 6건(Medium)은 중첩 use cache 의 루트 파라미터 노출, 바이너리 인자로 인한 캐시 키 충돌, 직접 운영 환경의 공유 셸 캐시 오염, 압축 응답 헤더 불일치로 인한 응답 뒤바뀜, Edge 라우트(Edge 런타임에서 도는 경로)의 쿠키 값 헤더 노출, 이미지 최적화의 SVG 차단 우회입니다.

여러 항목은 Cache Components 를 켠 경우나 next start(Next.js 를 직접 서버로 띄우는 명령)로 직접 운영하는 경우에만 해당합니다. Next.js 로 여러 사용자나 테넌트의 데이터를 캐시하는 서비스에 특히 중요합니다.

> 확인할 점: Next.js 를 쓰는 서비스라면 버전과 Cache Components · Edge 라우트 사용 여부를 확인하고 패치 버전으로 올립니다.

출처: [Next.js 블로그: November 2026 Security Release](https://nextjs.org/blog/november-2026-security-release) · [Next.js 블로그: 사전 공지](https://nextjs.org/blog/upcoming-nextjs-security-release-november-2026)

### 2. Kernel 이 유출된 API 키에서 시작해 로깅 업체와 호스팅 계정까지 번진 보안 사고를 공개했습니다.

`인프라·보안` · 2026-11-04

브라우저 세션을 제공하는 Kernel 은 2026-11-04 보안 사고 공지를 올렸고, 전체 고객의 0.28% 가 영향을 받았다고 밝혔습니다. 사고는 11-02 고객 문의로 처음 인지됐습니다.

공지에 따르면 공격자는 10-24 유출된 API 키로 내부 프로필 데이터를 읽었습니다. 10-27 에는 같은 키로 로깅 서비스 업체의 직원 로그인에 접근해, 일부 API 키와 고객 앱의 외부 비밀 값이 든 데이터를 내려받았습니다.

11-03 에는 탈취한 호스팅 계정 자격 증명으로 GPU 서버 4대에 접근해 암호화폐 채굴을 시도했습니다. Kernel 은 자격 증명 폐기와 교체, IP 차단, 서버 격리를 했고, 범위를 좁힌 API 키와 키 사용 네트워크 통제를 재발 방지책으로 내놓았습니다.

키 하나가 로그 저장소를 거쳐 다른 비밀 값으로 번진 경로를 보여 주므로, 외부 로깅 서비스를 쓰는 모든 팀에 참고가 됩니다.

> 확인할 점: 애플리케이션 로그와 외부 로깅 서비스에 API 키나 비밀 값이 남지 않는지, 키를 바로 교체할 절차가 있는지 확인합니다.

출처: [Kernel 보안 사고 공지](https://www.kernel.sh/blog/public-notice-of-security-incident-nov-4-2026)

### 3. Spring Boot 4.2.0-RC2 가 나와 4.2 정식 출시가 가까워졌습니다.

`백엔드` · 2026-11-06

Spring 팀은 2026-11-06 Spring Boot 4.2.0 의 두 번째 출시 후보(RC2)를 냈습니다. 정식 출시 전에 마지막으로 문제를 찾는 단계입니다.

이번 RC2 에는 개선 · 문서 · 의존성 업그레이드 · 버그 수정 99건이 들어갔습니다. 공지가 꼽은 변경은 Reactor Netty(Spring WebFlux 가 쓰는 비동기 HTTP 서버)의 X-Forwarded-Prefix(프록시가 붙인 경로 앞부분을 전하는 HTTP 헤더) 지원과, spring.data.redis.database 설정이 master/replica(쓰기 서버와 읽기 복제 서버) 연결에도 적용되는 것입니다.

공지 글은 4.2 정식 출시일과 4.2 전체 새 기능 목록을 적지 않고 릴리스 노트로 안내합니다. Spring Boot 4.x 를 쓰는 팀이 다음 업그레이드를 미리 시험해 볼 수 있는 시점입니다.

> 확인할 점: Redis master/replica 구성에서 database 번호 설정을 쓰는지 확인하고, 정식 출시 전에 RC2 로 빌드와 테스트를 한 번 돌려 봅니다.

출처: [Spring 블로그: Spring Boot 4.2.0-RC2](https://spring.io/blog/2026/11/06/spring-boot-4-2-0-RC2-available-now/)
