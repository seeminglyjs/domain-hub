`방법론` · 2026-11-17

Neo4j(그래프 데이터베이스 회사)의 Morgan Sénéchal 은 2026-11-17 기업용 AI 지식 계층 연재의 3장으로 도메인 온톨로지(Domain Ontology, 업무 용어의 의미와 관계를 정해 둔 체계)를 만드는 방법을 공개했습니다. 글은 용어집(Glossary)이 용어를 설명만 할 뿐 업무 과정 · 데이터 · 담당자와 연결하거나 강제하지 못한다는 문제에서 출발합니다. 가상의 은행에서 "고객을 얼마나 잃었나"에 세 팀이 3.2% · 1.1% · 4.7% 로 답한 것은 계산 오류가 아니라 이탈(churn) 정의가 달랐기 때문이라고 설명합니다.

방법은 업무 용어를 DataConcept 노드로 두고 정의 · 상태(proposed · canonical · superseded) · 유효 기간 · 출처를 붙이며, 측정 속성은 DataAttribute 노드로, 검사할 수 있는 규칙은 BusinessRule 노드로 나누는 것입니다. 승인 담당자는 사람이 아니라 역할(Role)에 연결해, 담당자가 바뀌어도 책임이 이어지게 합니다. 파이프라인이 자동으로 뽑은 연결은 신뢰도와 함께 제안 상태로만 들어가고, 스튜어드(Steward, 승인 담당자)가 승인해야 표준 정의가 됩니다. 정의는 드물게 바뀌고 기준값은 자주 바뀌므로, 기준값을 규칙에 두어 정의를 고치지 않고 바꿀 수 있게 합니다. 같은 이름의 지표를 팀마다 다르게 계산하는 조직에서 정의와 담당자를 함께 관리하려는 사람에게 쓸모 있습니다.

> 확인할 점: 지표 정의를 코드나 문서로 관리하는 서비스라면, 정의마다 승인 상태 · 유효 기간 · 담당 역할이 기록되어 특정 날짜에 어떤 정의가 쓰였는지 조회할 수 있는지 확인합니다.

### 2. Neo4j 가 데이터 웨어하우스의 테이블을 옮기지 않고 그래프로 질의하는 Virtual Graph 를 정식 출시했습니다.

`제품` · 날짜 미확인(게시 정보 2026-11-16, 시간대 미확인)

Neo4j 는 데이터 웨어하우스(Data Warehouse, 여러 원천의 데이터를 분석용으로 모아 둔 저장소) 안의 테이블을 복사하지 않고 그 위에 그래프를 만드는 Virtual Graph 의 정식 출시(GA, General Availability)를 알렸습니다. 사용자가 Cypher(Neo4j 의 그래프 질의 언어)로 질의하면 Virtual Graph 가 이를 SQL 로 바꿔 웨어하우스 안에서 실행하고 결과만 돌려받습니다. 변환은 결정적이어서 같은 질의는 늘 같은 SQL 이 되고, EXPLAIN 으로 생성된 SQL 을 볼 수 있습니다.

웨어하우스의 역할 · 행 단위 제한 · 마스킹이 그대로 적용되며, 지원 원천은 Snowflake(클라우드 데이터 웨어하우스 회사) · Databricks(데이터 · AI 분석 플랫폼 회사) · BigQuery(Google 의 클라우드 데이터 웨어하우스) · S3(AWS 의 객체 저장소)에 둔 Apache Iceberg(대용량 분석용 오픈 테이블 형식) 테이블입니다. 현재 Google Cloud 의 Neo4j Aura(Neo4j 의 클라우드 관리형 서비스)에서 쓸 수 있고, AWS · Azure 는 곧 지원한다고 밝혔습니다. 글은 응답에 초~분 단위가 걸려도 되는 읽기 전용 분석용이며, 트랜잭션 처리 · 계속되는 쓰기 · 밀리초 단위 탐색에는 맞지 않고 OPTIONAL MATCH · 최단 경로 문법 같은 일부 Cypher 기능이 빠져 있다고 적습니다. 관계 중심 분석을 하고 싶지만 데이터를 그래프 DB 로 옮기는 비용과 권한 관리가 부담인 데이터 팀에게 쓸모 있습니다.

> 확인할 점: 관계 탐색 분석을 위해 데이터를 그래프 DB 로 복사하려는 서비스라면, 복사 대신 원천에서 질의를 변환하는 방식으로 필요한 응답 시간과 질의 기능이 충족되는지 먼저 확인합니다.

## 기술 소식

### 1. OpenJDK 의 Base64 디코더 하드웨어 가속 경로에서 원격 코드 실행으로 이어질 수 있는 메모리 손상 취약점(Java4Shell)이 공개되었습니다.

`인프라·보안` · 2026-11-17 · 보도

보안 회사 Calif 는 2026-11-17 OpenJDK HotSpot(OpenJDK 의 기본 JVM 구현)의 x86-64 Base64 디코더 인트린직(Intrinsic, JIT 컴파일러가 특정 메서드를 CPU 전용 명령으로 바꾸는 최적화)에서 힙 경계 밖 쓰기 취약점 CVE-2026-114938 을 공개하고 Java4Shell 이라고 이름 붙였습니다. CVSS(Common Vulnerability Scoring System, 취약점 심각도 점수) 4.0 점수는 9.2 이며, 글은 공개 당일 OpenJDK 권고와 Oracle 의 2026년 11월 정기 보안 업데이트(Critical Patch Update)가 함께 나왔다고 적습니다. 영향 범위는 OpenJDK 17.0.6 이상과, 이를 바탕으로 만든 Temurin · Corretto · Oracle Java SE 같은 배포판입니다.

취약 경로는 AVX-512 VBMI(일부 x86-64 CPU 의 확장 명령어 묶음)를 지원하는 CPU 에서만 쓰이며, ARM64 는 영향을 받지 않습니다. java.util.Base64 디코더가 C2 JIT(자주 쓰는 코드를 기계어로 다시 컴파일하는 HotSpot 컴파일러)로 컴파일된 뒤 형식이 어긋난 Base64 입력을 받으면 힙 메모리가 손상됩니다. 인증 처리 · 파일 업로드 · 네트워크 메시지 처리처럼 외부 입력을 Base64 로 푸는 곳이 모두 경로가 될 수 있으며, 연구진은 Spring Boot 와 Apache Struts 로 만든 예제 앱, Keycloak · Jenkins 같은 제품의 기본 설정에서 원격 코드 실행을 시연했다고 밝혔습니다. 패치 전 임시 조치로는 JVM 옵션 -XX:-UseBASE64Intrinsics 로 가속 경로를 끄는 방법이 제시되었습니다. 이 노트는 OpenJDK · Oracle 의 권고 원문을 직접 열어 확인하지 못했으므로 보도 표시를 붙입니다.

> 확인할 점: x86-64 서버에서 Java 서비스를 돌린다면, 쓰는 JDK 배포판의 2026년 11월 보안 업데이트 적용 여부와 CPU 의 avx512vbmi 지원 여부를 확인하고, 바로 올릴 수 없으면 -XX:-UseBASE64Intrinsics 적용을 검토합니다.

### 2. Next.js 팀이 2026년 보안 권고가 51건으로 늘어난 이유와, 취약한 버전을 쓰면 개발 · 빌드 때 알려 주는 기능을 설명했습니다.

`프론트` · 2026-11-17

Next.js 팀은 2026-11-17 보안 권고 수가 2024년 6건 · 2025년 14건 · 2026년 51건(글 작성일 기준)으로 늘어난 이유를 설명했습니다. 글은 AI 로 오래된 버그를 찾는 비용이 낮아진 것을 주된 이유로 들며, 올해 취약점의 70%는 1년 이상, 43%는 3년 이상 된 코드에서 나왔다고 밝힙니다. 이미지 최적화가 쓰는 외부 이미지 라이브러리에서 나온 취약점도 많아, 메모리 안전한 코덱으로 바꾸는 작업을 진행하고 있다고 적습니다.

보안 수정은 대략 한 달에 한 번, 미리 알린 일정으로 나옵니다. Next.js 16.4 부터는 next dev 와 next build 가 지금 버전이 알려진 취약점에 해당하면 경고하고, 개발 도구 화면에도 같은 안내가 표시됩니다. 호스팅 환경과 프레임워크 사이의 해석 차이로 생기는 우회를 줄이려고, 배포 환경이 따라야 할 계약인 어댑터(Adapter)를 정식화하고 있다고도 밝혔습니다. Next.js 를 쓰는 팀이 보안 업데이트 주기를 계획하는 데 쓸모 있습니다.

> 확인할 점: Next.js 를 직접 띄우는 서비스라면, 월 단위 보안 릴리스 공지를 받는 담당자와 적용 기한이 정해져 있는지, 16.4 이상에서 빌드 로그의 취약 버전 경고를 누가 보는지 확인합니다.

### 3. Databricks 가 객체 저장소 위에 만든 Postgres 서비스에서 페이지 읽기의 99% 이상을 로컬 캐시로 처리하는 계층 구조를 공개했습니다.

`데이터·DB` · 2026-11-17

Databricks 블로그는 2026-11-17 Lakebase Postgres(Databricks 의 관리형 PostgreSQL 서비스)가 객체 저장소(Object Storage, 대량 데이터를 싸고 안전하게 보관하지만 응답이 느린 저장소)에 데이터를 두면서도 질의마다 그곳을 읽지 않는 구조를 설명했습니다. 구조는 네 층으로, 영구 상태가 없는 Postgres 계산 노드와 로컬 페이지 캐시, WAL(Write-Ahead Log, 변경 기록)을 다수결로 복제하는 Safekeeper, WAL 을 페이지로 바꿔 로컬 NVMe 디스크에 두는 Pageserver, 오래된 이력을 보관하는 객체 저장소입니다.

읽기는 로컬 캐시, Pageserver, 객체 저장소 순서로 내려가며, 아래 층에서 가져온 것을 위 층이 캐시하므로 깊이 내려가는 비용은 한 번만 냅니다. 운영 표본 수치로 페이지 접근의 약 99.46%가 계산 노드 캐시에서, 약 0.54%가 Pageserver 에서 처리되었고 객체 저장소 요청은 초당 약 39건이었다고 밝힙니다. 계산 노드가 영구 상태를 갖지 않으므로 브랜치 · 복원이 데이터 복사 없는 메타데이터 작업이 되고, 쓰지 않을 때 계산 노드를 0대로 줄일 수 있습니다. 느린 저장소 앞에 캐시 층을 설계하는 개발자에게 참고가 되는 사례입니다.

> 확인할 점: 느린 원천 앞에 여러 층의 캐시를 두는 서비스라면, 층마다 적중률과 가장 아래 층까지 내려간 요청 수를 따로 집계하고 있는지 확인합니다.

### 4. PostgreSQL 대량 적재 도구 pg_bulkload 에서 갈라져 나와 읽기 · 파싱을 병렬로 나눈 pg_fastload 1.0.0 이 공개되었습니다.

`데이터·DB` · 2026-11-17

postgresql.org 뉴스에 2026-11-17 오픈소스 프로젝트 pg_fastload 1.0.0 공개 글이 실렸습니다. pg_bulkload(PostgreSQL 에 대량 데이터를 빠르게 넣는 확장 도구) 3.1.23 의 소스를 갈라 만든 도구로, 기존 제어 파일 문법과 로그 형식을 유지합니다. PostgreSQL 공식 릴리스가 아니라 외부 프로젝트이며, PostgreSQL 15~19 를 지원하고 BSD 3-Clause 라이선스입니다.

적재를 입력 읽기 · 레코드 파싱 · 튜플(Tuple, DB 안의 행 하나) 만들기 · 삽입 네 단계로 나누고, 앞의 세 단계는 백그라운드 워커가 병렬로, 삽입은 하나의 백엔드가 순서대로 처리합니다. 적재 전체가 한 트랜잭션이라 잘못된 행 하나가 적재 전체를 중단시키며, NOT NULL · CHECK 제약이나 STDIN 입력 같은 13가지 조건에서는 순차 경로로 돌아갑니다. 저자 자체 측정으로 1GiB CSV(약 737만 행, 16 vCPU)에서 1.37초가 걸려 COPY FROM 의 8.32초보다 약 6배 빨랐다고 밝히지만, 요약에 적힌 일부 배율은 본문 표와 맞지 않습니다. 초기 적재나 대량 이관 시간이 문제인 PostgreSQL 사용자에게 검토 대상이 될 수 있습니다.

> 확인할 점: 대량 이관 시간이 문제인 서비스라면, 외부 도구를 들이기 전에 COPY · 인덱스 나중 생성 · 커밋 묶기만으로 줄어드는 시간을 먼저 측정합니다.
