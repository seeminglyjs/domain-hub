## 도메인 소식

### 1. Databricks 가 전력 회사 Constellation 이 부서마다 다른 '고객' 정의를 하나로 맞춘 공용 데이터 기반 구축 사례를 공개했습니다.

`사례` · 2026-11-12

Databricks(데이터 · AI 분석 플랫폼 회사)는 2026-11-12 블로그에서 미국 청정 전력 생산 기업 Constellation 이 Databricks 위에 공용 데이터 플랫폼을 만든 사례를 소개했습니다. Constellation 은 소매 · 도매 · CRM(Customer Relationship Management, 고객 관리 시스템) 쪽이 '고객'을 각자 다르게 정의해, '고객이 몇 명인가'라는 질문에 부서마다 다른 답이 나오는 문제를 겪었습니다. 2026년 Calpine(미국 발전 회사) 인수로 정의와 저장소가 다른 시스템이 더 늘어난 것도 배경입니다.

회사는 사업 책임자와 합의한 공통 엔터티(Conformed Entity, 여러 부서가 같은 정의로 쓰는 업무 개념)를 한 번 정의하고 여러 작업 공간에서 다시 쓰게 했습니다. Unity Catalog(Databricks 의 데이터 · 권한 · 계보 관리 기능)가 계보와 세밀한 접근 권한을 맡고, 거버넌스(Governance, 데이터의 의미와 사용 규칙을 정하고 지키게 하는 체계)는 '데이터 의미의 주인이 누구인가'에 답하는 소유 모델로 다룹니다.

글은 발전소 정비 계획 · 영업 기회 우선순위 같은 초기 활용 사례를 들며, 정비 계획에서는 결정을 담당 팀에 남긴다고 적습니다. 성과 수치는 공개하지 않았습니다. 같은 업무 용어를 부서마다 다르게 쓰는 조직이 정의 합의와 소유자 지정부터 시작하는 순서를 보여 주는 사례입니다.

> 확인할 점: 부서마다 같은 이름의 지표를 다르게 계산하는 서비스라면, 그 용어의 정의마다 승인한 소유자가 정해져 있는지 확인합니다.

## 기술 소식

### 1. PostgreSQL 이 보안 취약점 52건을 고친 지원 버전 업데이트와 19 RC 2 를 내고, 14 버전 지원을 끝냈습니다.

`데이터·DB` · 2026-11-12

PostgreSQL 글로벌 개발 그룹은 2026-11-12 18.7 · 17.12 · 16.16 · 15.20 · 14.25 업데이트와 PostgreSQL 19 의 두 번째 출시 후보(RC, Release Candidate)를 냈습니다. 이번 업데이트는 보안 취약점 52건과 버그 140건 이상을 고쳤고, 공지 표에는 CVSS(취약점 심각도 점수) 8.8 의 임의 코드 실행 항목이 다수 있습니다.

14.25 는 PostgreSQL 14 의 마지막 업데이트이며, 이후 14 버전은 보안 · 버그 수정을 받지 않습니다. 업데이트는 누적 방식이어서 덤프 · 복원이나 pg_upgrade(메이저 버전 사이 데이터 변환 도구) 없이 서버를 멈추고 실행 파일만 바꾸면 됩니다.

다만 GIN 인덱스(배열 · JSON · 전문 검색에 쓰는 역색인) 손상, pg_trgm(문자열 유사 검색 확장) GiST 인덱스 손상, 길이 없이 선언한 bpchar(공백을 채우는 고정 길이 문자 자료형) 컬럼의 B-tree 인덱스 문제를 고친 만큼, 해당 인덱스는 업데이트 뒤 REINDEX 가 필요할 수 있습니다. 증분 백업을 쓰는 서버는 업데이트 뒤 새 전체 백업을 받아 이후 증분 백업의 기준으로 삼으라고 공지는 안내합니다. PostgreSQL 19 정식 출시는 2026-11-19 로 예정되어 있습니다.

> 확인할 점: PostgreSQL 14 를 쓰는 서비스라면 지원 버전으로 올리는 일정을 잡고, 지원 버전을 쓰는 서비스라면 업데이트 뒤 GIN · pg_trgm GiST · 길이 없는 bpchar B-tree 인덱스가 있는지 찾아 REINDEX 대상을 정합니다.

### 2. Microsoft 365 에서 서버 다수가 예상치 않게 쓸 수 없게 되며 Outlook · Teams 등이 여러 시간 장애를 겪었다고 보도되었습니다.

`아키텍처·운영` · 2026-11-12 · 보도

TechCrunch(미국 기술 매체)는 2026-11-12 Microsoft 365 의 Outlook 메일 · Teams · SharePoint · OneDrive · Copilot 등에 접속 장애가 났다고 보도했습니다. 처음에는 미주 지역 문제로 알려졌다가, 이후 모든 지역 사용자가 영향을 받을 수 있다고 Microsoft 가 밝혔습니다.

보도에 따르면 Microsoft 는 많은 서버가 예상치 않게 쓸 수 없게 되어 남은 인프라에 부하가 몰렸다고 설명했고, 트래픽 급증이나 공격 때문은 아니라고 밝혔습니다. 복구 조치로는 배포 중단, 전 세계 인프라로 연결 트래픽 재분배, 영향받은 서버 재시작, 헬스 체크(Health Check, 서버가 정상인지 주기적으로 확인하는 검사) 관련 실패 조건을 우회하는 설정 변경 시험이 전해졌습니다.

서버가 왜 쓸 수 없게 되었는지와 헬스 체크가 원인인지는 보도 시점까지 확인되지 않았고, Microsoft 의 사후 분석 보고서도 아직 나오지 않았습니다. 일부 서버가 멈추면 남은 서버로 부하가 옮겨 가며 장애가 넓어지는 연쇄 과부하의 모양을 보여 주는 사례입니다.

> 확인할 점: 헬스 체크에 실패한 서버를 자동으로 제외하는 로드 밸런서(Load Balancer)를 쓰는 서비스라면, 서버 여러 대가 한꺼번에 제외될 때 남은 서버가 부하를 감당하는지와 한 번에 제외될 수 있는 서버 비율에 상한이 있는지 확인합니다.
