## 도메인 소식

### 1. Databricks 가 앱 세션 안에서 고객별 금융 상품 제안의 순위를 매기는 실시간 다음 최선 제안(Next Best Offer) 예제를 공개했습니다.

`방법론` · 2026-11-16

Databricks(데이터 · AI 분석 플랫폼 회사)는 2026-11-16 소매 은행이 앱 세션 안에서 고객에게 가장 맞는 금융 상품 제안을 고르는 실시간 다음 최선 제안(Next Best Offer) 예제를 공개했습니다. 학습과 서빙에서 특징값(Feature, 모델 입력값) 계산을 따로 구현하면 두 값이 어긋나므로, Feature Views(특징값을 한 번 선언해 학습과 서빙에 함께 쓰는 Databricks 기능)로 정의를 하나로 모은 것이 핵심입니다.

일괄 계산 특징값은 오프라인 테이블과 온라인 저장소에 함께 저장하고, Kafka(대용량 이벤트 스트리밍 플랫폼) 이벤트로 만든 실시간 특징값은 온라인 저장소에만 둡니다. 학습 때는 원천 이벤트에서 각 사건 시점의 값을 다시 계산해 미래 값이 섞이지 않게 합니다. LightGBM(트리 기반 머신러닝 라이브러리) 순위 모델이 40개 제안 전체에 점수를 매기며, 글의 요약은 특징값 조회와 추론을 합친 순위 계산이 p95(요청 100건 가운데 95번째로 느린 응답 시간) 34ms 라고 적습니다. 다만 본문 측정 절에는 p95 48ms 로 적혀 있어 두 수치가 서로 맞지 않습니다.

글은 순위 계산이 최종 제안 결정이 아니며, 운영 전에 자격 · 동의 · 적합성 · 억제 조건을 따로 더해야 한다고 밝힙니다. 실시간 추천 구조를 설계하는 개발자와, 모델 점수와 업무 규칙의 경계를 정해야 하는 담당자에게 쓸모 있는 예제입니다.

> 확인할 점: 추천 점수로 제안을 고르는 서비스라면, 점수 계산 뒤에 자격 · 동의 · 노출 횟수 제한을 확인하는 단계가 코드에 따로 있는지 확인합니다.

## 기술 소식

### 1. Optimizely Web 스크립트를 통해 178개 조직 웹사이트에 카드 정보와 암호화폐 주소를 노리는 악성 JavaScript 가 배포되었다고 보안 연구자가 발표했습니다.

`인프라·보안` · 2026-11-16 · 보도

보안 연구자 Scott Helme(웹 보안 감시 서비스 Report URI 의 창업자)는 2026-11-16 Optimizely(웹 화면 A/B 시험 · 개인화 도구 회사)의 Optimizely Web 스크립트를 통해 178개 조직 웹사이트에 악성 JavaScript 가 배포되었다고 발표했습니다. 공격자는 고객 프로젝트의 'Project JavaScript' 칸에 외부 스크립트를 불러오는 코드를 써 넣었고, 이 파일은 Optimizely 의 CDN(Content Delivery Network, 정적 파일을 여러 지역에서 나눠 전달하는 서비스)에서 정상 인증서와 함께 그대로 전달되었습니다. 글은 CDN 캐시 오염이 아니라고 밝히며, 공격자가 여러 고객 프로젝트의 쓰기 권한을 어떻게 얻었는지는 아직 모른다고 적습니다.

불러온 스크립트는 화면과 클립보드의 암호화폐 지갑 주소를 바꿔치기하고, 사이트 자체 입력 양식에 적은 카드 정보를 가로채고, HttpOnly(스크립트가 읽지 못하게 막는 쿠키 속성)가 아닌 쿠키를 공격자 서버로 보냈습니다. 결제 대행사의 별도 결제 창(iframe)에 입력한 카드 정보는 영향을 받지 않았다고 글은 밝힙니다. 글이 확인한 영향 조직 호스트 256개 가운데 68개는 콘텐츠 보안 정책(CSP, Content Security Policy, 브라우저가 불러올 수 있는 스크립트와 연결 대상을 제한하는 응답 헤더)이 없었고, 스크립트 실행 자체를 막은 곳은 24개였습니다.

StepSecurity(소프트웨어 공급망 보안 회사)는 'strict-dynamic' 방식의 CSP 가 신뢰한 스크립트가 추가로 불러온 스크립트를 막지 못한다고 덧붙였습니다. 보도 시점까지 Optimizely 의 공식 설명은 나오지 않았습니다.

> 확인할 점: 외부 A/B 시험 · 분석 · 광고 스크립트를 쓰는 서비스라면, 결제 · 로그인 화면에서 그 스크립트를 제외했는지와 CSP 의 script-src · connect-src 가 허용 목록으로 좁혀져 있는지 확인합니다.

### 2. Microsoft 가 11월 12~13일 Microsoft 365 장애의 원인을 7월 수정에 들어간 결함과 그 뒤에 이어진 연쇄 과부하로 설명했다고 보도되었습니다.

`아키텍처·운영` · 2026-11-16 · 보도

The Register(영국 기술 매체)는 2026-11-16 Microsoft 가 11-15 공개한 예비 사후 분석 보고서를 보도했습니다. 원인은 2026년 7월에 배포한 수정에 들어 있던 결함으로, 부하가 높을 때 Windows 내부 프로세스에서 락 경합(Lock Contention, 여러 스레드가 같은 잠금을 기다리며 밀리는 상태)을 일으켜 CPU 와 메모리를 다 써 버렸습니다. 이 결함은 코어가 많은 최신 하드웨어에서 더 심했는데, Microsoft 는 부하 시험이 코어가 적은 하드웨어 위주로 이루어져 결함을 놓쳤다고 밝혔습니다.

11-12 01:07 UTC 에 Teams 트래픽이 Exchange Online 과 함께 쓰는 주 게이트웨이로 옮겨 왔고, 그때 게이트웨이 용량의 약 14%가 이미 서비스에서 빠져 있었습니다. 멈춘 서버의 트래픽이 다음 정상 서버로 옮겨 가 같은 결함을 일으키면서, 두 시간 안에 전체로 퍼져 가장 나빴을 때 80% 넘는 서버가 응답하지 않았습니다. 서버를 다시 넣어도 몰린 부하에 곧 다시 멈췄고, 자동 복구도 이렇게 넓은 무응답 상태를 다루도록 설계되지 않았다고 보고서는 적습니다.

결함이 몇 달 된 것이라 단순히 되돌릴 수 없었으므로, 엔지니어들은 해당 코드 경로를 이전 정상 상태로 돌리는 업데이트를 만들어 서버 묶음별로 적용했습니다. 최종 보고서는 11-20 에 나올 예정입니다. 이 노트는 Microsoft 보고서 원문을 직접 열어 확인하지 못했으므로 보도 표시를 붙입니다.

> 확인할 점: 장애 서버의 트래픽을 남은 서버로 넘기는 구성이라면, 남은 서버가 같은 결함으로 연달아 무너질 때 넘기는 양을 제한하는 장치가 있는지와 부하 시험 장비가 운영 서버와 같은 사양인지 확인합니다.
